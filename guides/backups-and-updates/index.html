Back up Hermes before changing versions

A useful backup restores the agent’s state and your work, not just the code. Record the Agent and WebUI versions together, and prove recovery before relying on it.

Sources reviewed November 14, 2026.

Write down what must be recovered

Identify the active Hermes home, every named profile and the WebUI state directory. The WebUI state usually lives in the webui directory under the Hermes home; HERMES_WEBUI_STATE_DIR can override it. Record the paths your running service uses.

Include configuration, memories, skills, schedules, sessions, workspaces and important output files. Browser profiles, container volumes and external memory services may need separate backups. A Git checkout alone does not contain these.

Take a consistent, protected snapshot

  1. Pause scheduled jobs and stop all processes that can write the state you are copying.
  2. Use a supported database backup or copy the complete stopped state, including any database sidecar files.
  3. Encrypt sensitive backups and restrict access. They can contain account tokens, private conversations and authenticated sessions.
  4. Keep recovery keys separately from routine agent access, with a tested way for the operator to retrieve them.

Choose and record the release

Read the release notes and compatibility guidance first. The project tests WebUI releases with the corresponding Agent release available at that time; mixing arbitrary versions is unsupported. Record both versions and the source revision or image digest.

The website installer clones the repository’s current default branch and updates it with git pull; it does not pin a stable release. For Docker, stable and experimental are different channels. Follow the matching Docker instructions, especially for multi-container source volumes.

Start the new combination in an isolated test setup. Check sign-in, a test chat and tool call, saved settings and scheduled-job behavior before restoring normal traffic.

Prove the restore and rollback path

Restore into a separate test location first, with jobs, outbound messages and sensitive integrations disabled. Check that the expected sessions and files are present. Do not run two writers against the same state.

If the new version migrated data, switching back to the older version may not be enough. Keep the pre-upgrade snapshot and matching versions as a pair. Never test a downgrade against your only copy of production state.
