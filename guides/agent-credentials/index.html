Practical guide · Credentials

Let your agent sign in.
Keep its access limited.

A password vault can protect stored credentials. It cannot make an agent harmless once that agent can unlock the vault, use a secret, or act in a logged-in browser.

Start with the smallest account that can do the job

New to this? Start with row one below: give the agent its own account and sign in yourself. Add a vault integration only when you need it.

Use a dedicated account for the agent where the service allows it. Give it access to the specific project, folder or workspace it needs. Keep your personal email, financial accounts, vault administration and recovery credentials separate.

Prefer an official API or OAuth connection with limited scopes when the task does not require the website. If it needs a browser, sign in yourself in a browser profile reserved for the agent.

Check the features Hermes Agent already provides

The current Agent vault documentation describes browser_vault: encrypted saved logins and origin-bound browser filling that keeps passwords out of model messages. It can also use signed-in Bitwarden or 1Password CLIs. Availability depends on your Agent version and client. The documented interactive prompts are in CLI, TUI and Desktop; do not assume a WebUI or headless API session can answer them. Prepare access through a supported interactive surface first.

The default local vault key is stored beside the encrypted vault, so a copy of that home directory can include both. The documented OS-keychain option changes backup and unattended-access behavior; it does not isolate secrets from programs running with your privileges. Review those trade-offs before moving the key.

For API keys, Agent's secret sources separately support Bitwarden Secrets Manager and 1Password at startup. This is different from website password filling. Follow the installed version's setup instructions, retain a protected bootstrap credential and verify its scope. Neither feature makes arbitrary plugins or shell execution safe.

Bitwarden, Vaultwarden, Secrets Manager: which does what

Bitwarden Password Manager

The password manager stores website logins and other vault items. Its bw CLI has separate authentication and unlock steps: logging in with a personal API key does not remove the need to unlock before reading encrypted vault data. The session key decrypts the vault. Protect it like the master password. Read the CLI documentation.

For an agent, prefer a dedicated account with only the needed items. A folder in your personal vault does not restrict what an unlocked CLI session can read.

Vaultwarden

Vaultwarden is an unofficial Bitwarden-compatible server. It can be a useful self-hosted password-vault choice, but you take on patching, TLS, access restrictions, backups and recovery. Follow the project's hardening guide and verify compatibility with the client version you use. Do not assume it implements Bitwarden Secrets Manager or that bws can use it as a replacement server. Project and documentation.

Bitwarden Secrets Manager

This is a separate product for machine-accessible secrets. Its bws CLI authenticates with a machine-account access token. Assign each job its own machine account, limited to the projects it needs, with Can read permissions. Protect the access token as carefully as the secrets it can retrieve. Machine account documentation.

A first step outside the agent conversation

For ordinary website work, start by signing in yourself in the agent’s dedicated browser profile. For a supported Hermes Agent vault integration, follow the linked upstream interactive setup rather than pasting a password into WebUI.

If you are configuring the Bitwarden CLI yourself, these commands belong in your private terminal, not an agent tool or a recorded session. Install the official CLI first. Configure a dedicated account; never share its personal API credentials with chat.

# Password Manager: authenticate, unlock, then lock when finished
bw login --apikey
bw unlock
bw lock

bw login --apikey authenticates; unlocking is separate. bw unlock prints sensitive session material. Keep it out of transcripts. A bw get result can likewise disclose a password if its output is captured.

For a trusted scheduled script, configure BWS_ACCESS_TOKEN through your scheduler’s secret store, with a narrowly scoped machine account. Then the documented Secrets Manager command injects secrets into that script’s environment:

# Example script name: supply your own reviewed job
bws run -- './nightly-report.sh'

This does not print the secrets by itself, but the script can read and expose them. Review the script, secret names and logging; do not run an unrestricted agent under this command and assume its secrets are hidden. This is a Secrets Manager example, not a Vaultwarden command.

A practical flow for website logins

  1. Create the account and limit it. Give the agent only the permissions required for its recurring task.
  2. Use a separate browser profile. Keep personal accounts and unrelated sessions out of the browser the agent controls.
  3. Sign in yourself first. Handle MFA or a passkey interactively. Do not weaken a service's authentication just to automate it.
  4. Approve the task and its boundaries. Reading a report, sending a message, changing permissions and spending money are different levels of access.
  5. Check what the agent can see and do. Browser tools may capture page text, screenshots, downloads and network details. A masked password field does not guarantee clean screenshots or tool logs.
  6. End or retain the session deliberately. A session retained for future jobs is an ongoing credential. Protect its files and revoke it when no longer needed.

Cookies count as credentials. A saved browser state can let someone act as the account without knowing its password. Keep it out of prompts, attachments, screenshots and repositories, including private ones. Playwright's authentication guide explains the same risk for saved test sessions.

For unattended work, design the unlock path too

A scheduled job needs some way to authenticate before it can retrieve a secret. Moving the website password into a vault does not solve where the vault's own access token or unlock capability lives.

Keep the bootstrap token in your OS keychain or the scheduler's secret store when supported. Limit which operating-system account can access it, which processes inherit it, and which secrets the workload can retrieve. Environment variables can be useful for delivery, but they are not an encryption boundary: child processes, diagnostics or a compromised process may expose them.

For browser automation, a small credential broker can accept an approved site and item identifier, retrieve the secret outside the model conversation, and submit it to a restricted browser action. Check the supported Agent vault flow above before building a custom broker. A custom broker is a separate implementation you must enforce and test; describing one does not install it in WebUI.

The agent asks to sign into the approved reporting account. A separate component checks the exact destination, obtains only that credential, performs the login and returns a status—without returning the password to the model.

Enforce destinations and permissions in code, not only in a prompt. Restrict redirects and the browser's account privileges. Website text is untrusted input and must not expand which vault items or sites the broker permits. bw serve defaults to localhost. Do not expose it using --hostname all.

Four rules for limiting exposure

A broker can keep passwords out of model messages. It does not protect against a compromised agent or host.

  • Keep raw secrets out of model context. Do not paste passwords, master passwords, access tokens, recovery codes or vault exports into chat, memory files, skills or mailbox messages.
  • Keep outputs clean. Secret-retrieval CLI commands often print their result. Do not run them through a tool that records stdout into the conversation. Disable tracing and check logs and failure paths for accidental output.
  • Limit runtime access. An agent with terminal access as the same OS user may invoke bw itself or read its unlock material. Separate the agent with a dedicated OS user or a container, and restrict which credentials, files and helpers cross that boundary.
  • Separate high-impact actions. Require a human for changes such as granting access, rotating recovery methods or making purchases unless the owner has explicitly authorized a bounded workflow.

Make stopping access part of the setup

Document how to stop the job, revoke the vault or machine-account token, end website sessions and rotate exposed credentials. Deleting a local token file does not revoke it at the service. Bitwarden says revocation immediately blocks new authentication, but an already authenticated machine can retain secret access for up to an hour. Rotate affected secrets when access must stop sooner.

When finished with the Password Manager CLI, lock or log out of the vault and remove no-longer-needed session material from the process environment. That does not invalidate a website login already created with the password; revoke the website's own sessions separately.

For Vaultwarden, test encrypted backups and recovery before depending on it. Keep recovery material outside the agent's routine access. Start with a low-risk test account and confirm that unauthorized items, redirects and sensitive actions are refused.
